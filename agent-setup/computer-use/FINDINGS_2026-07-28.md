## Claim 1 — nested Hyprland works: **CONFIRMED**

```
host   instance ..._1785184062_840778133  pid 23432   wl socket: wayland-1
nested instance ..._1785197416_882125046  pid 616900  wl socket: wayland-2
```

Verified working:

## Claim 2 — input fidelity: **BROKEN, and it's not what the doc thinks**

Typed `ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789` into a **shell-free sink**
(`ghostty -e /bin/sh -c 'exec cat > file'`) so no prompt, rc-file, completion,
or vi-mode could interfere.

| Method | Clean | Result |
|---|---|---|
| `wtype` default | **0/12** | `ABCDEFGHIJKLM<TAB>PQRSTUVWXYZ0123456789` |
| `wtype -d 25` (delayed) | **0/3** | identical corruption |
| `wtype` per-character | **3/3** | correct |
| clipboard `wl-copy` + paste | **3/3** | correct |

**`N` and `O` are consumed and replaced by a single `Tab`.** Deterministic —
12/12 byte-identical, not flaky.

Two things follow:

1. **Slowing down does not help.** This is *not* a timing/rate race — `-d 25`
   corrupts identically. It is a bug in the temporary virtual-keyboard keymap
   `wtype` generates.
2. **It affects the host compositor identically** (0/3 clean on host, in a
   controlled focused window). So `hcu-type` has been **silently corrupting
   text in every agent GUI interaction** long enough to trip the bug — and
   `wtype` exits 0 every time, so the tool layer reports success.

### Correction: the trigger is position, not distinct-character count

An initial model — "more than 13 *distinct* characters overflows the keymap" —
was **wrong**, and a 28-distinct shell command line typing cleanly disproved it.
A direct probe (`test/probe-trigger.sh`, raw wtype) gives:

| string | chars | distinct | shifted | result |
|---|---|---|---|---|
| `abcdefghijklmnopqrstuvwxyz` | 26 | 26 | 0 | clean |
| `ABCDEFGHIJKLMNOPQRSTUVWXYZ` | 26 | 26 | 26 | **corrupt at pos 14** |
| `abcdefghijklmn` | 14 | 14 | 0 | clean |
| `ABCDEFGHIJKLMN` | 14 | 14 | 14 | **corrupt (N dropped)** |
| `ABCDEFGHIJKLM` | 13 | 13 | 13 | clean |
| lowercase + digits | 36 | 36 | 0 | clean |
| `a!@#$%^&*()_+{}\|:"<>?` | 21 | 21 | 20 | **corrupt at pos 14** (`{}`→Tab) |
| `git commit -m "fix: …"` | 48 | 28 | 3 | clean |
| 80 chars of `ab` | 80 | 2 | 0 | clean |

Distinct count does not predict it (36 distinct clean, 14 distinct corrupt).
Every observed corruption lands at **character position 14 or later**, and only
where shift-requiring characters sit at that position. The exact upstream
mechanism is not fully characterised — this is an empirical boundary, not a
derived one.

**Fix adopted:** never let a single `wtype` invocation exceed 13 characters.
That is conservative by construction (no call can reach the position where
corruption starts), independent of the unexplained shift interaction, and far
faster than per-character typing. `--strategy paste` remains available as a
hard guarantee for untrusted text.

Separately, `wtype` has no option terminator — `--` is typed literally, and any
argument beginning with `-` is parsed as a flag and types **nothing**, silently.
Leading dashes are therefore emitted as `-k minus` key presses.

## Claim 3 — the oracle problem, demonstrated accidentally

First run used a normal `ghostty` inheriting the personal zsh config. Sequence:

```
wtype drops a char → command mangled → shell enters `(` continuation
→ zsh vi-mode falls to NORMAL → all later "typing" swallowed as vi commands
→ every wtype call still exits 0
```

Three actions in a row reported success while accomplishing nothing. Only a
screenshot revealed the true state (`NORMAL` in the prompt, bell in the title).

This is exactly the oracle problem the original QA research prompt asked about,
reproduced locally in ten minutes. **Tool-level success ≠ effect.** Any runtime
built here must verify effects, never trust exit codes.

## Claim 4 — clean teardown: **FAILS as specified**

`SIGTERM` to the nested compositor removed its socket (so `hyprctl instances`
showed 1, looking clean) but **left the process alive**. Two orphaned Hyprland
processes survived and needed `SIGKILL`.

A session manager must reap by PID with escalation, and must not trust
`hyprctl instances` as the liveness oracle.

## Claim 5 — the deterministic verifier: **now working** (`bin/pw-init`)

`playwright-cli` runs through `npx` with no global install, but out of the box
it cannot launch a browser on NixOS. Three routes were tried:

| route | outcome |
|---|---|
| Playwright's bundled chromium | fails — binaries are FHS-linked, "OS is not officially supported" |
| `--browser chrome` channel | fails — looks for `/opt/google/chrome/chrome`, no such path here |
| nixpkgs `playwright-driver.browsers` | unusable — npx ships playwright-core **1.62.0-alpha**, nixpkgs is **1.58.2**; browser revisions do not match |
| **`launchOptions.executablePath` → system chromium** | **works** |

`bin/pw-init` writes the working config (system chromium resolved at runtime,
plus `--no-sandbox --disable-setuid-sandbox --disable-dev-shm-usage
--disable-gpu`, without which headless chromium launches and immediately dies).

Verified end-to-end by `test/test-playwright.sh` (5/5): loads a page, reads
state, obtains a **semantic element ref** from the accessibility snapshot, acts
on it, observes the state actually change, and captures a failed network request
in the console channel. Headless throughout — nothing appears on the desktop.

Two gotchas worth remembering: `playwright-cli` **blocks `file://` URLs**, so
test pages must be served over HTTP; and the `executablePath` is a nix store
path, so `pw-init` must be re-run after a chromium version bump.

This gives the division the design document argued for, and it now actually
runs here: **browser-use explores, Playwright proves.**

## Claim 6 — pixel capture dies when the monitor is off (found overnight)

Working unattended while the workstation was idle, every `grim` capture began
failing — host and nested alike. Initially recorded as DPMS sleep; that was
wrong, and the corrected mechanism is below.

```
$ grim /tmp/x.png
no wl_output
$ hyprctl monitors -j | jq length
0
```

When the physical monitor is off, **every DRM connector reports
`disconnected`** and Hyprland drops the output entirely — `hyprctl monitors`
returns zero. This is NOT DPMS: `hyprctl dispatch dpms on` does not bring it
back, because there is no connected output to wake. Verified 2026-07-28 over
SSH with the monitor powered off:

```
$ cat /sys/class/drm/card1-DP-1/status
disconnected
$ hyprctl dispatch dpms on && hyprctl monitors -j | jq length
0
``` A nested session still reports its own virtual output
(`WAYLAND-1`), so checking the *session's* monitor list is misleading — but the
nested compositor is a Wayland client of the host, its surface is never
presented, it receives no frame callbacks, never renders, and
`wlr-screencopy` blocks forever waiting for a frame that cannot arrive.

Consequences:

- **Any unattended workflow that depends on screenshots will hang**, not fail
  fast, unless the capture is bounded by a timeout.
- **There is no remote workaround.** Tried and failed: `dpms on` (nothing to
  wake); a nested `hyprctl output create headless` (created, but stays `0x0` —
  assigning a mode reports `ok` and changes nothing on 0.54.3); `cage` headless
  (cannot open the DRM device, Hyprland holds it). Pixel work requires the
  monitor to be physically on.
- Everything structured keeps working: `hyprctl clients` (window graph, titles,
  geometry), CDP/Playwright, the filesystem. Only pixels go away.

This is the strongest practical argument for the channel hierarchy the design
document recommends. It is not a style preference — on an idle machine the
pixel channel is simply **absent**, while the structured ones are unaffected.

`acu-session capture` now pre-flights the host output count and fails with that
explanation instead of a mystery timeout.

## Claim 7 — nested sessions poisoned the systemd user environment (real damage)

`acu-session` caused a user-visible outage, and it is worth recording exactly
because the symptom appeared **six hours after** the tool had exited.

A nested Hyprland imports **its own** `WAYLAND_DISPLAY` into the `systemd --user`
manager on startup and never restores it:

```
before nested session : WAYLAND_DISPLAY=wayland-1
during                : WAYLAND_DISPLAY=wayland-2   <- clobbered
after teardown        : WAYLAND_DISPLAY=wayland-2   <- left stale
```

Consequence on 2026-07-28: an overnight session left `wayland-2` behind. At
08:01 the wallpaper timer restarted `omarchy-swaybg.service`, which read the
stale value, could not connect, and crash-looped **334 times**:

```
Jul 28 08:01:06 swaybg: Unable to connect to the compositor.
                        ... check or set the WAYLAND_DISPLAY environment variable.
```

A concurrent agent session diagnosed the mechanism correctly but cleared this
tool on the grounds that *"none of those processes are even running right now,
so they're not the cause"*. **Not running is not the same as not causal** —
persistent state outlives the process that wrote it. Ownership of a side effect
lasts as long as the state does, not as long as the process does.

Fix: `_restore_systemd_wayland_display`, called inline right after start (so the
exposure window is seconds, not the session lifetime) and again at the very end
of teardown. Two details found by testing rather than reasoning:

- Restoring *before* the compositor is reaped loses a race — a shutting-down
  instance re-imports its own display. The restore must come after the kill.
- Restoring "whatever was there before" is wrong when the previous value was
  itself stale. The repair is **self-healing**: a value is only accepted if its
  socket actually exists, else it falls back to the live host display.

Verified across a clean lifecycle and a simulated crash (SIGKILL, no teardown);
both end at `wayland-1`.

## Assessment of `research.md` itself

**It never answered the six questions that were actually asked.** The prompt
asked for prior art, the oracle problem, persona-diversity research, cost/scale
numbers, reproducibility, and auto-patch safety. The document contains no prior-art
survey, no cost figures, and no research on any of it — it cites the Hyprland
wiki, Apple developer docs, and one arXiv paper (MCPWorld). It pivoted to
architecture opinion. **Those six questions remain open.**

Its architectural instincts are nonetheless sound, and the local probe supports
the core ones: channel hierarchy (API → a11y → pixels), event-driven waits over
screenshot polling, stable window identity over regex matching, and
`browser-use` discovers / Playwright proves.

But it is scoped as a multi-month platform (`agent-computerd`, Rust crates, Nix
modules, compositor plugins, eight new skills, Skill Contract v2) while the
things that would make today's tooling trustworthy are small and unbuilt.
